## 一、定位澄清:它不是「代码脚手架」

容易被误读的一点,先说清楚:

- 本仓**不生成任何应用代码**。`src/` 只有一个空的 `__init__.py`(README 目录树标注为"业务代码(待填)")。
- 全仓**没有**技术选型、模块分层模板、CRUD 生成器、接口定义骨架。

它真正的定位是:**给已有代码加一层「AI 交付纪律」的治理层**(规则 + 技能 + 十阶段 + 门禁 + 留痕),
而不是像 `create-react-app` / Spring Initializr 那样的项目起步器。

**它是容器,不是内容。**

## 二、适用前提:为「存量项目」设计,不是为「新项目」

`BluePrint.md` §0 明写适用场景:

> 存量企业级项目,多模块、RPC 框架、流程引擎、配置中心、分布式缓存、全套中间件,**代码量十万行级以上**。

而 `USAGE.md` §五「复制前准备」要求你**已经拥有**:项目架构图、事故报告、Code Review 意见、
编码规范、分层规范、CI/CD 配置、DDL、接口文档、脱敏线上请求。

14 个填充 Agent 的输入**全部是既有产物**:

| Agent | 输入(必须先存在) |
| ----- | ----------------- |
| 架构解析 | `harness/sources/architecture/`、现有 `src/` |
| 事故反推 | `harness/sources/incidents/` |
| Review 提炼 | `harness/sources/reviews/` |
| 代码考古 | 现有 `src/` |
| 数据建模 | DDL / OpenAPI / 流程图 |
| 门禁解析 | 现有 CI、`Makefile` |

**结论**:新项目**没有可填的原料**。对新项目使用本仓,跑到填充阶段会得到空输出或编造内容
——而"编造"正是本仓三道闸要拒绝的东西。**它适合存量项目,不适合从零起步。**

## 六、可以信什么、还不能信什么

**可以信的——门禁机制。**

它真的会跑、会拦、可重复,并通过了**反向验证**(把门禁改坏,测试必须变红)。
骨架从"看起来有门禁"变成了"确实有门禁"。

**还不能信的——方法论的有效性。**

1. 本仓**从未有过真实需求走过十阶段**。已做过一次**机制空跑**(模板占位符),它证明了
   流水线的**机制**可用,但**证明不了**这套流程在真实需求上是否可行、负担多重
   —— 那需要真实需求,以及真实的人来走那五个人工确认点。
2. 20 份规则**全是空骨架**,因此当前的实际约束力 ≈ 只有 `scripts/check_python_rules.py`
   里实现的那 8 条硬检查(金额 float / HTTP timeout / 裸 except / print / eval / 密钥 / 时区 / 复杂度)。
3. `BluePrint.md` 与 `README.md` 里
   **AI 代码率 24.86% → 90.54%** 之类的数字,**来自本仓借鉴的另一个团队的项目**,
   **不是本仓的实测**。本仓的实测使用数据是**零**。

> 一句话:**工具可信,工具的用处未被证明。**

## 七、可复用资产(脱离本骨架也能用)

`scripts/` 下的这几个脚本**不依赖本仓其余部分**,可直接搬进任何 Python 项目:

| 脚本 | 作用 |
| ---- | ---- |
| `check_pytest_report.py` | 堵"测试全绿"的三种假象:一条没跑 / 有 skip 冒充通过 / 报告缺失 |
| `check_python_rules.py` | 8 条可程序化硬规则(PRICE/HTTP/ERR/LOG/SEC/TZ/PY 等) |
| `check_secrets.py` | 密钥扫描(支持 `pragma: allowlist secret` 行级豁免) |
| `check_harness_docs.py` | 文档结构与代码围栏校验(锚点 + 目录 + 形状 + 围栏配平) |
| `stage_gate.py` | 阶段状态机:前置阶段 passed **且产出物现在依然存在**才放行;断点续跑 |

另有**作为流程文档**可脱离代码库采用的部分:
十阶段流水线、五个人工确认点、**三道防编造闸**(来源强制 / 可执行强制 / 测试强制)。

## 八、启用(或复活)条件

本仓要产生**已证明**的价值,需要同时满足:

1. 手上有一个**存量 Python 项目**(而非新项目);
2. 能拿出**≥5 份脱敏事故报告 + ≥20 份 Code Review 意见 + ≥1 份架构文档**;
3. 走 `USAGE.md` **方式 B**:把 `harness/` + `scripts/` 并入该项目仓库;
4. 按顺序跑 6 个核心填充 Agent → 人工审核 → 回填规则(**每条同时交付检查脚本 + 能失败的测试**);
5. **先跑空跑 REQ-0000**(用 `make state` 走十阶段),记录体系缺陷并 Patch;
6. 再拿一个真实需求试点。

**条件不满足时,本仓的合理形态就是「不绑定项目的方法论范本」**
——这正是 `USAGE.md` 方式 A,是**设计内的一种用法**,不是失败状态。

## 十、封存说明(2026-09-11)

**本仓已停止演进**,封存为「方法论的参照范本」—— 即 `USAGE.md` 的**方式 A**。

**为什么封存**:缺少可填充的真实来源。本仓为**存量项目**设计(§二),
而填充所需的原料(事故 / Review / 架构 / DDL / 遗留代码)目前不存在;
在缺原料的情况下继续写规则与模板,产出的是**编造内容**,而这正是本仓三道闸要拒绝的。
**停手是本仓自身逻辑下的正确动作,不是失败。**

**封存 ≠ 废弃** —— §七 列出的资产仍可独立使用:

- `scripts/` 下 5 个门禁脚本可直接用于任何 Python 项目
- 十阶段 / 五个确认点 / 三道防编造闸可作为流程文档采用

**不在维护范围**:依赖版本漂移、规则填充、试点、观测接线。

**重新启用时**:先跑 `pre-commit run --all-files` 与 `make gate`。
`.pre-commit-config.yaml` 的 `rev` 与 pip 装的版本**靠人守同代**(§九 第 3 条),
隔一段时间很可能需要先对齐版本;CI 若变红通常就是这个原因。

**复活条件**:见 §八。

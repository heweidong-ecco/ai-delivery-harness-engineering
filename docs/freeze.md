## ⚠ 工作方式变更记录:本仓修正**不走 PR**(2026-09-11)

**变更内容**:对本仓库(`ai-delivery-harness-engineering`)的修正,
**不需要走 PR,直接 `commit` + `push` 到 `main`**。

**变更原因**:业主明确指示(2026-09-11)。本机无 `gh` CLI,且当前为单人多机的
骨架维护阶段,PR 流程在此场景下是纯开销。这与上文解冻记录里
「每次填充必须走 PR → 以『最小留痕』替代」是同一取向的延续。

**留痕替代方案**:

1. 提交信息按 `scripts/check_commit_msg.py` 的规范(`<type>: <subject>`),
   并在正文写明**变更依据**(外审工单编号 H1–H14、patch-log 条目等);
2. 每条修正登记在 `harness/iteration/patch-log.md` §五「已 Patch 清单」;
3. 重要变更同步 `CHANGELOG.md`。

**⚠ 与仓库自身规则的冲突(已知并被显式覆盖)**:本仓**自己写着**「必须走 PR」——
`README.md` Q7「Agent 能直接改 main 吗?**不能。必须走 PR**」、
`harness/iteration/patch-log.md` §七「**禁止 Agent 直接改 main**」、
`harness/agents/README.md` §八「直接改 main」列为禁止项。

业主是所有者和最终决策人,此覆盖**有效**;但记录在此,以免日后读仓库规则的人
以为这些条文仍然生效。**若本仓要作为"方法论范本"对外发布**(USAGE 的方式 A),
这条偏离必须先解决 —— 因为范本自身违反自己的规则,是最坏的反例。

**恢复条件**:重新冻结、或对外发布范本之前,应恢复「走 PR」并要求至少一人审核
(`CONTRIBUTING.md` §PR 规范)。

## 📦 封存记录:2026-09-11 **停止演进**

**决定**:本仓**停止演进**,封存为「方法论的参照范本」——即 `USAGE.md` 的**方式 A**
(不绑定具体项目)。业主决定。

**原因**:缺少可填充的真实来源。本仓是为**存量项目**设计的(`BluePrint.md` §0),
14 个填充 Agent 的输入**全部是既有产物**(事故报告 / Code Review / 架构文档 / DDL / 遗留代码)。
在没有这类来源的情况下继续"完善",产出的会是**编造内容**而非完成度 ——
而那正是本仓三道防编造闸要拒绝的东西。
**所以停手不是妥协,是本仓自身逻辑下的正确动作。**

**封存时的状态**(全部实测):

- `make gate` 全绿(137 测试);`pre-commit run --all-files` 16/16 且幂等
- 骨架 100% 完成;**填充 0%、试点 0%**
- 十阶段完成过一次**机制空跑**(机制可用;暴露 4 条缺陷,已修 —— 见 `harness/pilot/findings.md`)
- 方法论有效性**未被验证**(从未有过真实需求走过)

**封存 ≠ 废弃**:

- `scripts/` 下 5 个门禁脚本可**脱离本骨架**直接用于任何 Python 项目
- 十阶段 / 五个人工确认点 / **三道防编造闸**可作为**流程文档**单独采用
- 清单见 `docs/project-status.md` §七

**不在维护范围**:依赖版本漂移、规则填充、试点、观测接线。

> ⚠ 长期不用后若重新启用,请先跑 `pre-commit run --all-files` 与 `make gate` ——
> `.pre-commit-config.yaml` 的 `rev` 与 pip 装的版本**靠人守同代**(见 patch-log X19/X20),
> 隔一段时间很可能需要先对齐版本。CI 若变红,通常就是这个原因。

**复活条件**:见 `docs/project-status.md` §八(需**存量项目** + ≥5 事故 + ≥20 Review)。

**关联**:`docs/project-status.md`(现状与验收)、`harness/pilot/findings.md`(空跑实证)、
`harness/iteration/patch-log.md` §四(全部缺陷记录)。

# 空跑发现

## 一、本仓实测:机制空跑(2026-09-11)

> **目的**:只验证**机制**,不验证**方法论**。
> 用 `harness/changes/_template/` 的占位符走完十阶段(做法见 `USAGE.md` 验证 5:
> `mkdir -p harness/changes/REQ-0000 && cp harness/changes/_template/*.md harness/changes/REQ-0000/`)。
>
> **实测结论:机制可用** —— 状态机、增量门、回滚全部按设计工作;
> 同时暴露出 **3 条缺陷**(见 1.2),它们此前都没有任何机制能发现。

### 1.1 机制验证通过的项目(实证)

| 验证项 | 实测结果 |
| ------ | -------- |
| 十阶段状态机 | 阶段 1–9 依次 `enter` + `pass` 全部通过;第 10 阶段精确拦截 |
| **前置门禁** | 跳过前置阶段直接 `enter 编码实现` → `rc=1`,报"前置门禁未过" |
| **产出物校验** | 第 10 阶段 `pass` → `rc=1`,报 `产出物缺失/为空: harness/checkpoints/REQ-0000-HC5.md` |
| **回滚** | 删掉第 1 阶段产出物后,`resume` **一路退回起点**(报"最后有效通过的阶段:(无)"),而不是取"最高的已通过阶段" |
| **增量门** | `check-gates.sh REQ-0000 --stage 1 / 9 / 10` 累积正确,各自 `rc=0` |
| **入口链路** | `make gates REQ=REQ-0000` 与 CI 的 "Check stage gates" 步逻辑(glob `harness/changes/REQ-*`)在真实需求目录上均正常工作 |
| `resume` 终态 | 十阶段全通过后报"所有阶段已通过且产出物齐备,无待续" |

> 这说明 H4/H5 的修复是**真的**:阶段门不再是口号,产出物被删会被发现,断点能续跑。

#### 旁证:门禁抓到了**修正者自己**的回归

封存当天改 `README.md` 横幅时,为了写清状态多加了 3 行,把 H1 标题挤到了第 11 行。
**本仓自己的门禁当场报错**:

```text
Harness docs check FAILED (1 项):
  - README.md: 前 10 行内没有 H1 标题
```

压缩横幅后恢复。这件事值得单独记下来,因为它比任何"我们修好了"的声明都更有说服力:

- 门禁**不是只在有人特意去测试时才工作** —— 它在日常改动里自动生效;
- 它拦的是**改门禁的人自己** —— 没有"自己人豁免";
- 拦的理由**可读、可定位、可修**(直接指出文件与前 10 行的规则)。

同类旁证还有:提交空跑产物时 `end-of-file-fixer` 拦下了 state 文件(空跑-4)——
**两条链路(pre-commit 与 make gate)都在真的盯着**。

### 1.2 空跑发现的缺陷(待处理)

| 编号 | 缺陷 | 证据 | 影响 |
| ---- | ---- | ---- | ---- |
| **空跑-1** | **阶段 10 的产出物没有模板,也不在「必须文件」清单里**。`harness/changes/_template/` 只给 7 个文件,`harness/checkpoints/` 只有一个格式说明 `README.md`,**没有模板文件**;而 `stages.json` 要求阶段 10 产出 `harness/checkpoints/<REQ>-HC5.md` | 走完阶段 1–9 后阶段 10 必然 `rc=1`;必须**手工**按 `checkpoints/README.md` 的格式造一个文件才能过 | 照文档执行的 Agent 会在**最后一阶段**卡在一个**从未被告知要产出**的文件上;而 `changes/_template/README.md` 的「必须文件」清单里也没有它 |
| **空跑-2** | **文档规定的复制命令会把模板自己的 README 带进需求目录**。`USAGE.md` 验证 5 与 `_template/README.md` 都写 `cp _template/*.md`,而 `*.md` 包含模板的 `README.md` | `harness/changes/REQ-0000/` 里多出 `README.md`(模板说明) | 每个需求目录都会多一份与业务无关的文件;它不在任何产出物清单里,是纯噪音 |
| **空跑-3** | **五个人工确认点里,只有 HC-5 被机器校验**。`human-checkpoints.md` 声称 HC-1 ~ HC-5 且"**未确认不得进入下一阶段(阻塞)**",但 `stages.json` 只把 `checkpoints/<REQ>-HC5.md` 列为阶段 10 的产出物 —— HC-1(需求评审后)、HC-2(计划评审后)、HC-3(编码评审后)、HC-4(部署前)**完全没有门禁** | `stages.json` 中带 `checkpoints` 产出物的阶段只有「用户确认」一个 | **与 H4/H5 同型**:写下来的约束没有机制。"五个人工确认点必须人工"目前是**纯文字**,4/5 无人守 |
| **空跑-4** | **状态机写的 state 文件没有行尾换行 → 每个含状态变更的提交都要提交两次**。`stage_gate.py:_save()` 用 `write_text(json.dumps(state, ensure_ascii=False, indent=2))`,不带末尾换行;而本仓 pre-commit 的 `end-of-file-fixer` 要求文件以换行结尾 → 每次提交它都会改这个文件并**中止提交** | 提交本次空跑产物时实测:第一次 `git commit` **失败**,钩子输出 `Fixing harness/state/REQ-0000.json`;最小复现:调用 `_save()` 后文件末尾字符为 `'}'` | 状态文件按设计是**要入库**的(`docs/state` 的说明即如此),所以这是**每次状态变更都要付出**的摩擦。`collect_metrics.py:29` 有同样写法,但其输出目录被 gitignore,故未被钩子看到(属潜在同类问题) |

> 四条都不是"设计错了",而是**设计与机制之间的缝隙** —— 正是本仓反复强调要消除的东西。

### 1.3 处理结果(2026-09-11 当天修复)

| 编号 | 修法 |
| ---- | ---- |
| 空跑-1 | 新增 `harness/checkpoints/_template.md`;并在 `harness/changes/README.md` 的产出物清单里**显式注明阶段 10 的产出物不在这七件套里**;`checkpoints/README.md` 补「模板」一节与复制命令 |
| 空跑-2 | **去根因**(而不是在 7 处文档贴补丁):把模板说明并入 `harness/changes/README.md`,删除 `_template/README.md` —— 于是 `_template/` 里**只剩交付物**,文档里那句 `cp _template/*.md` **一个字都不用改就自动正确** |
| 空跑-3 | 按"如实标注、不编机制"处理:`human-checkpoints.md` 与 `checkpoints/README.md` 都明确写出**只有 HC-5 有机制,HC-1 ~ HC-4 是纯文字**,并注明"要上机制需先定清各自的证据" |
| 空跑-4 | `stage_gate.py:_save()` 与 `collect_metrics.py` 写出时补 `"\n"`(后者输出目录被 gitignore,属同类潜在问题一并修) |

> 验证:`harness/changes/_template/` 的 `*.md` 计数 = 7(只剩交付物);
> 门禁与测试全绿(见提交信息)。
